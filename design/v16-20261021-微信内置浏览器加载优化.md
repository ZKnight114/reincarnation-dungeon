# v16 微信内置浏览器加载优化

用户反馈手机仍加载异常缓慢，并确认使用微信内置浏览器、进度并未完全停止。已确认当时GitHub Pages脚本与本地最新构建相同，上一轮修复已发布。

## 本轮处理

旧方案只在Service Worker可接管时拥有素材持久缓存；内置浏览器的支持和权限可能不同。此外，首次完整入场会产生213个媒体请求，资源总量13,569,061字节，约13.6MB，GitHub Pages慢链路的请求开销较明显。本轮不将桌面加载成功等同于微信实机验收，也不声称已测得用户手机的准确瓶颈。

- 微信优先使用页面内素材缓存，不依赖后台Worker。其他浏览器继续优先原Worker，无法接管时也启用页面缓存。
- 页面缓存优先复用原有`guild-image-hashes-v1:<path>` CacheStorage及已完成的SHA-256文件。CacheStorage不可用时，使用独立`guild-media-hashes-v1:<path>` IndexedDB，只保存素材，不触碰游戏存档。
- 首次没有哈希缓存时，由构建生成的15个二进制包获取完整213项素材。资源包和每个拆出文件均做SHA-256核验，再逐个持久写入；下载进度按收到的字节与准备数量共同显示，能看到已下载MB数。原图片、音频质量与字节未改变，总下载字节也未减少；优化的是请求数量。
- 已有素材缓存时，使用单项文件更新，不使用整包更新。首个文件成功写入即登记已有缓存，避免中断后再次整包下载；读取旧Worker缓存的少量样本也可识别已缓存状态。
- 图片从本地Blob载入，运行时图片地址和CSS背景同步替换为已准备的资源；人物拼接／头像仍能拿到对应解码图片。进入典籍、人物等页面不会为了画背景再请求原PNG。
- 缓存读写有时限。权限拒绝后不会为每个文件重复等待；配额不足停止写入，但已缓存文件继续可读。资源包失败回退为单文件下载，不影响已有缓存。
- 保留首次全量准备、既有失败重试、播放开关和存档。首次访问的实际速度仍受微信到GitHub Pages的网络吞吐影响，未承诺固定加载秒数。

## 验证

独立验收服务器显式禁用Service Worker和CacheStorage，标记内置浏览器UserAgent，实际使用浏览器IndexedDB。所有资源响应`Cache-Control: no-store`，排除普通HTTP缓存。此为受限环境模拟，并非真实微信客户端。

| 场景 | 资源包网络请求 | 单项媒体网络请求 | 页面缓存统计 |
| --- | ---: | ---: | --- |
| 首次全量入场 | 15 | 0 | 准备213项 |
| 刷新 | 0 | 0 | 213项命中、0下载 |
| 仅更改一张PNG后刷新 | 0 | 1 | 212项命中、1下载 |

进入典籍与招募加点页，图标、书架、按钮和拼接人物正常，没有新增资源请求或浏览器错误。测试位于独立5205端口，未改变用户线上或5190现有培养进度。变更只在验收服务器临时返回PNG附加字节和对应清单，正式素材未修改。

构建验证核验所有包的完整哈希及每个单项范围，检查包恰好覆盖全部213项，同时保持网页、离线单文件及旧启动／存档恢复检查。自动测试覆盖无Worker的持久缓存、改名复用、单文件更新、失败不污染缓存、首载包并发去重、CSS地址复用。

完整自动测试386项通过，构建及资源包校验通过。记录：`qa/mobile-loading-tests.txt`、`qa/mobile-loading-build.txt`、`qa/mobile-cache-network.jsonl`、`qa/mobile-cache-proof.json`、`qa/mobile-cache-character.jpg`。

## 发布

本轮本地修改和构建，不自动提交、推送或部署。需发布本次源码和生成的离线HTML，GitHub Actions会生成含资源包的完整dist。发布后可使用`?v=16-mobile-cache`参数打开网址，帮助获取新的入口HTML，原素材缓存按哈希继续保留。最终实际加载速度仍需用户手机微信确认。
